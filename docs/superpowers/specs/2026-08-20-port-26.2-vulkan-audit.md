## MAJOR FINDING (2026-08-20, session 2): 3D world-space rendering is NOT a
## rename, it's a full API paradigm change

Verified against real 26.2 decompiled source (see "Reference source" section
below for path), not guessed -- per explicit instruction this session: don't
repeat the 1.21.4->26.1.2 mistake of compiling clean but being semantically
wrong, verify everything against real source before writing replacement code.

**`Tesselator`/old `BufferBuilder.begin()` pattern is gone entirely.** The
new pattern (confirmed via `net/minecraft/client/renderer/
DebugCrosshairRenderer.java`, a real vanilla example that builds a static
mesh once and draws it every frame):

1. Build: `ByteBufferBuilder.exactlySized(sizeInBytes)` (AutoCloseable,
   own the allocation) -> `new BufferBuilder(byteBufferBuilder,
   PrimitiveTopology.LINES/QUADS/etc, vertexFormat)` (note:
   `PrimitiveTopology` in `com.mojang.blaze3d`, replaces the old
   `VertexFormat.Mode` enum for this purpose) -> `.addVertex(...)` calls
   (same `VertexConsumer` interface as before, `BufferBuilder implements
   VertexConsumer`) -> `.buildOrThrow()` returns a `MeshData`
   (AutoCloseable).
2. Upload: `RenderSystem.getDevice().createBuffer(labelSupplier, usageFlags,
   meshData.vertexBuffer())` -> a `GpuBuffer`. This is a REAL GPU buffer
   upload, not a per-frame immediate draw -- vanilla's own example builds
   this ONCE in a constructor and re-draws the SAME `GpuBuffer` every frame.
3. Draw (every frame): `RenderSystem.getDevice().createCommandEncoder()
   .createRenderPass(labelSupplier, colorTextureView, clearColor,
   depthTextureView, clearDepth)` -> `RenderPass` (AutoCloseable, try-with-
   resources) -> `.setPipeline(RenderPipeline)` (a NEW concept, replaces
   loose GL state like blend func / depth test -- pipelines are
   pre-declared, e.g. `RenderPipelines.LINES`,
   `RenderPipelines.LINES_DEPTH_BIAS`) -> `.setVertexBuffer(slot,
   buffer.slice())` -> `.setIndexBuffer(...)` -> `.setUniform("Name",
   gpuBufferSlice)` (uniforms are named + GPU-buffer-backed, see this
   project's own `reference_postpass_live_uniform_trick.md` memory for a
   related COPY_DST buffer trick already learned in 26.1.2 -- likely still
   relevant/needed here) -> `.drawIndexed(...)`.

**Separately, there is ALSO a higher-level "Feature Renderer / Submit Node"
system** (`net/minecraft/client/renderer/feature/ShapeOutlineFeatureRenderer.
java` is vanilla's own real example, used for block-selection-outline-shaped
things): you define a `FeatureRendererType`, a `Submit` record describing
WHAT to draw (pose, shape, color, width), and a `buildGroup(...)` method
that batches multiple `Submit`s into vertex data via a `VertexConsumer` it
hands you (so `VoxelShape.forAllEdges` + `VertexConsumer.addVertex` still
works the SAME as our current `ShapeRenderer.renderShape` -- that part of
our code's logic is fine, only the surrounding plumbing changed). This
system integrates with vanilla's own per-frame render-state collection
pass, NOT something a mod can trivially opt into without either registering
with vanilla's feature-renderer registry (deep integration, high risk of
being wrong in ways that only show up at runtime) or reimplementing the
low-level path #1-3 above directly ourselves (more code, but self-contained
and easier to verify).

**SUPERSEDED by a much better finding below (`net.minecraft.gizmos`) --
do NOT reimplement the low-level GpuBuffer/RenderPass path by hand for
world-space ESP boxes/lines.** Left the paragraph above for context on how
this was reasoned through, but the actual recommendation is the Gizmos API.

## MAJOR FINDING #2 (same session): `net.minecraft.gizmos.Gizmos` -- vanilla's
## own reusable per-frame world-space drawing facility, use this directly

Found by looking for a vanilla example that rebuilds its mesh every frame
(the open question from finding #1). `net/minecraft/client/renderer/debug/
EntityHitboxDebugRenderer.java` (real vanilla file, read in full) draws
per-entity hitbox cuboids every frame via `Gizmos.cuboid(entity.
getBoundingBox().move(offset), GizmoStyle.stroke(color))` -- ONE line, no
manual buffer/pipeline management at all. This is a first-class vanilla API
(`net/minecraft/gizmos/` package, 14 files: `Gizmos`, `GizmoStyle`, `Gizmo`,
`GizmoCollector`, `SimpleGizmoCollector`, `GizmoProperties`,
`GizmoPrimitives`, and per-shape classes `CuboidGizmo`, `CircleGizmo`,
`LineGizmo`, `ArrowGizmo`, `RectGizmo`, `PointGizmo`, `TextGizmo`).

**API surface (`Gizmos.java`, read in full):**
- `Gizmos.cuboid(AABB, GizmoStyle)` / `cuboid(AABB, GizmoStyle,
  coloredCorner)` / `cuboid(BlockPos, GizmoStyle)` -- exactly our
  `renderBox`/`renderBoxOutline` use case.
- `Gizmos.line(Vec3 start, Vec3 end, int argb[, float width])`,
  `Gizmos.arrow(...)`, `Gizmos.circle(Vec3, radius, GizmoStyle)`,
  `Gizmos.rect(...)` (4 corners or cuboid-face+direction), `Gizmos.point(Vec3,
  argb, size)`.
- `Gizmos.billboardText(String, Vec3, TextGizmo.Style)` /
  `billboardTextOverBlock(...)` / `billboardTextOverMob(...)` -- world-space
  floating text, likely relevant for nametags/ESP text (KillEffectMemeRenderer,
  NameTagsModule -- verify separately, these currently use `MultiBufferSource`
  which may or may not still be the right path for THEIR specific use case,
  don't assume Gizmos covers everything MultiBufferSource did).
- `GizmoStyle` (record, read in full): `GizmoStyle.stroke(argb[, width])` (default
  width 2.5F), `GizmoStyle.fill(argb)`, `GizmoStyle.strokeAndFill(stroke,
  strokeWidth, fill)` -- maps 1:1 onto our existing Outline/Fill/Both render
  mode enum used throughout ESPModule/SpeedMineModule/etc, no redesign of our
  own settings needed, just a translation layer at the call site.
- Returns a `GizmoProperties` (fluent): `.setAlwaysOnTop()`,
  `.persistForMillis(int)`, `.fadeOut()` -- possibly useful for existing
  fade/animation logic in some render modules, worth checking case-by-case
  later rather than assuming.

**Why it's safe to call from our own render hooks, verified not assumed:**
Traced the full call chain in `net/minecraft/client/Minecraft.java` (real
vanilla main loop, read the relevant slice):
```java
try (TemporaryCollection ignored = this.levelRenderer.collectPerFrameRenderThreadGizmos()) {
    ...
    this.gameRenderer.render(this.deltaTracker, advanceGameTime);
}
```
`collectPerFrameRenderThreadGizmos()` (`LevelRenderer.java:974`) calls
`Gizmos.withCollector(this.renderThreadGizmos)` and wraps the ENTIRE
`gameRenderer.render(...)` call for the frame -- this is UNCONDITIONAL, not
gated behind any debug/F3 flag, runs every single frame regardless. Any mod
code that executes during that window (i.e. from our existing
`RenderWorldEvent`/render-related mixin hooks, which fire as part of
`gameRenderer.render(...)`) is guaranteed to have an active `GizmoCollector`
on the thread-local, so `Gizmos.cuboid(...)` etc. will NOT throw
`IllegalStateException: No GizmoCollector has been registered` and WILL get
picked up by `LevelRenderer.finalizeGizmoCollection()` ->
`DrawableGizmoPrimitives` -> the same `SubmitNode`/`FeatureRenderer` system
covered in finding #1 -- meaning gizmo draws are natively Vulkan-safe by
construction (vanilla wrote and tested this pipeline itself for the new
backend), we don't have to verify that part ourselves.

**Practical implication:** `Renderer3D.java`'s box/line rendering
(`renderBox`, `renderBoxOutline`, and whatever `EspShader.java` does) should
very likely be REWRITTEN to call `Gizmos.cuboid`/`Gizmos.line` directly
instead of porting the old `Tesselator`-based immediate-mode code at all --
this is almost certainly less code AND more correct than hand-rolling
`ByteBufferBuilder`/`BufferBuilder`/`GpuBuffer`/`RenderPass` ourselves, and
sidesteps the whole "did we get the new low-level GPU API right" risk
category entirely. Same likely applies to `Renderer2D.java`'s WORLD-SPACE
drawing calls if any exist (its GUI/screen-space calls go through
`GuiGraphicsExtractor` already and are unaffected, per finding in the
"Reference source" section below) -- audit `Renderer2D.java` call sites
individually to separate world-space (-> Gizmos) from screen-space (->
already-fine GuiGraphicsExtractor) usage before assuming one answer covers
the whole file.

**ANSWERED: ESP-through-walls IS supported, via `GizmoProperties.
setAlwaysOnTop()`.** Traced the full path: `LevelRenderer` submits gizmos in
TWO separate groups every frame (`finalizeGizmoCollection()`,
`LevelRenderer.java:295-297`) -- `standardPrimitives().submit(...,
onTop=false)` and `alwaysOnTopPrimitives().submit(..., onTop=true)`.
`SubmitNodeCollection.submitGizmoPrimitives` (read in full) routes
`onTop=true` into a distinct `this.alwaysOnTop` feature-render phase,
separate from the normal `this.gizmos` phase -- same architectural shape as
vanilla's own spectator/glow "see through walls" rendering. So: call
`Gizmos.cuboid(aabb, style).setAlwaysOnTop()` for ESP that should render
through walls, plain `Gizmos.cuboid(aabb, style)` (no `.setAlwaysOnTop()`)
for normal depth-tested boxes (e.g. block ESP that shouldn't x-ray). Maps
directly onto whatever "see through walls" boolean setting this mod's ESP
modules likely already expose -- just call `.setAlwaysOnTop()` conditionally
based on that existing setting value at the call site.
- Whether `Gizmos` calls have any per-frame budget/limit (debug systems
  sometimes cap primitive counts) -- check `DrawableGizmoPrimitives`/
  `GizmoPrimitives.java` if ESP with many boxes (e.g. block ESP scanning
  whole render distance) turns out to have a ceiling.
- `EspShader.java` specifically -- name suggests it does actual custom
  shader work beyond simple box/line drawing; check what it actually does
  before assuming Gizmos replaces it wholesale.

**`OutlineBufferSource` (Chams outline mechanism) -- separately confirmed
still fully gone**, not found under any package in the 26.2 jar. Given the
above paradigm shift, outline/glow rendering in 26.2 is almost certainly

session, same rigor as above (find vanilla's own current glow/outline

## Cross-check against a real released client's port (2026-08-20, session 2)

User pointed at Meteor Client's real 26.2 port commit for comparison:
https://github.com/MeteorDevelopment/meteor-client/commit/e43739752ea09d1ae044c6f33fe9f2a7a6238f58
(fetched full diff via `curl .../commit/<sha>.diff`, ~11.5k lines, grepped
for the symbols relevant to us rather than reading it all).

**Meteor does NOT use `net.minecraft.gizmos.Gizmos` anywhere (0 matches in
the whole diff).** They maintain their OWN pre-existing low-level renderer
(`MeshBuilder`/`MeshRenderer`/`MeteorRenderPipelines`, all pre-dating this
port, just updated for the new `PrimitiveTopology`/`IndexType`/pipeline
API surface) rather than adopting Gizmos. This doesn't invalidate the Gizmos
finding above (Gizmos may simply postdate when Meteor built their renderer,
or they value the extra control/customization a hand-rolled path gives them
over a debug-facility API) but it's a real signal worth weighing: Gizmos is
the LOWER-EFFORT path for us specifically because we don't have an existing
custom renderer to maintain, but it may have real limitations (styling,
performance at ESP scale, texture support) that Meteor's choice hints at
without confirming. **Decision on which path to take is NOT made yet** --
this is evidence for the next session's discussion, not a reversal of the
earlier recommendation.

**Confirmed from real code, useful regardless of which path we pick:**
- Meteor's `MeshRenderer.end()` uploads a FRESH vertex/index buffer to the
  GPU every single call via `mesh.uploadVertexBuffer(encoder)` /
  `uploadIndexBuffer(encoder)` -- i.e. per-frame dynamic GPU buffer upload
  is normal/acceptable in this new API, not something vanilla or real mods
  avoid. Answers the finding-#1 performance worry: it's fine.
- `RenderPipeline.getVertexFormatMode()` -> `getPrimitiveTopology()` /
  `getVertexFormatBinding(0)`, `pass.drawIndexed(indexCount, instanceCount,
  firstIndex, ...)`, `RenderPass` used with try-with-resources (matches the
  `DebugCrosshairRenderer` pattern from finding #1, cross-confirmed by an
  independent real codebase).
- **`OutlineBufferSource`/Chams -- real answer found, not TBD anymore.**
  Meteor's actual working Chams mechanism is
  `src/main/java/meteordevelopment/meteorclient/utils/
  OutlineRenderCommandQueue.java` (existing file, only touched/updated by
  this port commit -- meaning their REAL glow/outline approach already
  moved off `MultiBufferSource`/`OutlineBufferSource` before this port,
  probably back when 26.1.2's `SubmitNodeCollection` architecture first
  landed). It `extends SubmitNodeCollection` and overrides
  `submitModel`/`submitModelPart`/`submitBlockModel`/`submitItem`/etc to
  force their own fixed `outlineColor`/tint value into each call before
  delegating to `super.xxx(...)`. This is THE pattern for Chams in the
  modern (26.1.2+) architecture: don't touch buffer sources at all, override
  the submit-time color/outline parameter on the already-existing
  `SubmitNodeCollection` pipeline vanilla itself uses for every entity/block/
  item render. Two OTHER files (`CustomOutlineVertexConsumerProvider.java`,
  `NoopOutlineVertexConsumerProvider.java`, both `MultiBufferSource`/
  `OutlineBufferSource`-based) were DELETED entirely by this port commit --
  those were legacy/dead code, not the real mechanism, don't resurrect that
  pattern for our own port.
- Confirms `MultiBufferSource` really is gone with no direct replacement
  class -- every one of Meteor's ~15 files that referenced it either deleted
  the file outright or restructured around `SubmitNodeCollector`/
  `SubmitNodeCollection` instead (the same submit-based system, not a
  buffer-source swap-in).

**Revised priority for `OutlineBufferSourceMixin.java`**: rewrite around a
`SubmitNodeCollection` override (matching Meteor's `OutlineRenderCommandQueue`
shape) instead of trying to find a direct `OutlineBufferSource` replacement
class -- there isn't one, the whole approach changed. This is now the
