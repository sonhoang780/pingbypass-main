## MAJOR FINDING (2026-08-20, session 2): 3D world-space rendering is NOT a
## rename, it's a full API paradigm change

Verified against real 26.2 decompiled source (see "Reference source" section
below for path), not guessed -- per explicit instruction this session: don't
repeat the 1.21.4->26.1.2 mistake of compiling clean but being semantically
wrong, verify everything against real source before writing replacement code.

**`Tesselator`/old `BufferBuilder.begin()` pattern is gone entirely.** The
new pattern (confirmed via `net/minecraft/client/renderer/
DebugCrosshairRenderer.java`, a real vanilla example that builds a static
mesh once and draws it every frame):

1. Build: `ByteBufferBuilder.exactlySized(sizeInBytes)` (AutoCloseable,
   own the allocation) -> `new BufferBuilder(byteBufferBuilder,
   PrimitiveTopology.LINES/QUADS/etc, vertexFormat)` (note:
   `PrimitiveTopology` in `com.mojang.blaze3d`, replaces the old
   `VertexFormat.Mode` enum for this purpose) -> `.addVertex(...)` calls
   (same `VertexConsumer` interface as before, `BufferBuilder implements
   VertexConsumer`) -> `.buildOrThrow()` returns a `MeshData`
   (AutoCloseable).
2. Upload: `RenderSystem.getDevice().createBuffer(labelSupplier, usageFlags,
   meshData.vertexBuffer())` -> a `GpuBuffer`. This is a REAL GPU buffer
   upload, not a per-frame immediate draw -- vanilla's own example builds
   this ONCE in a constructor and re-draws the SAME `GpuBuffer` every frame.
3. Draw (every frame): `RenderSystem.getDevice().createCommandEncoder()
   .createRenderPass(labelSupplier, colorTextureView, clearColor,
   depthTextureView, clearDepth)` -> `RenderPass` (AutoCloseable, try-with-
   resources) -> `.setPipeline(RenderPipeline)` (a NEW concept, replaces
   loose GL state like blend func / depth test -- pipelines are
   pre-declared, e.g. `RenderPipelines.LINES`,
   `RenderPipelines.LINES_DEPTH_BIAS`) -> `.setVertexBuffer(slot,
   buffer.slice())` -> `.setIndexBuffer(...)` -> `.setUniform("Name",
   gpuBufferSlice)` (uniforms are named + GPU-buffer-backed, see this
   project's own `reference_postpass_live_uniform_trick.md` memory for a
   related COPY_DST buffer trick already learned in 26.1.2 -- likely still
   relevant/needed here) -> `.drawIndexed(...)`.

**Separately, there is ALSO a higher-level "Feature Renderer / Submit Node"
system** (`net/minecraft/client/renderer/feature/ShapeOutlineFeatureRenderer.
java` is vanilla's own real example, used for block-selection-outline-shaped
things): you define a `FeatureRendererType`, a `Submit` record describing
WHAT to draw (pose, shape, color, width), and a `buildGroup(...)` method
that batches multiple `Submit`s into vertex data via a `VertexConsumer` it
hands you (so `VoxelShape.forAllEdges` + `VertexConsumer.addVertex` still
works the SAME as our current `ShapeRenderer.renderShape` -- that part of
our code's logic is fine, only the surrounding plumbing changed). This
system integrates with vanilla's own per-frame render-state collection
pass, NOT something a mod can trivially opt into without either registering
with vanilla's feature-renderer registry (deep integration, high risk of
being wrong in ways that only show up at runtime) or reimplementing the
low-level path #1-3 above directly ourselves (more code, but self-contained
and easier to verify).

**SUPERSEDED by a much better finding below (`net.minecraft.gizmos`) --
do NOT reimplement the low-level GpuBuffer/RenderPass path by hand for
world-space ESP boxes/lines.** Left the paragraph above for context on how
this was reasoned through, but the actual recommendation is the Gizmos API.

**Why it's safe to call from our own render hooks, verified not assumed:**
Traced the full call chain in `net/minecraft/client/Minecraft.java` (real
vanilla main loop, read the relevant slice):
```java
try (TemporaryCollection ignored = this.levelRenderer.collectPerFrameRenderThreadGizmos()) {
    ...
    this.gameRenderer.render(this.deltaTracker, advanceGameTime);
}
```
`collectPerFrameRenderThreadGizmos()` (`LevelRenderer.java:974`) calls
`Gizmos.withCollector(this.renderThreadGizmos)` and wraps the ENTIRE

gated behind any debug/F3 flag, runs every single frame regardless. Any mod
code that executes during that window (i.e. from our existing

## Session 4: runtime crashes found via actual `runClient`, mixin-string audit

Compile-clean != mixin-apply-clean. Mixin `method="..."` name strings and `@Redirect`/`@ModifyArg`
INVOKE-target descriptor strings are plain strings to javac -- zero type-checking. Sponge Mixin only
validates them at class-load time, so a stale target crashes the game at BOOT (`MixinApplyError`/
`InvalidInjectionException`), never at `compileJava`. User pasted 2 real crash logs from
`gradlew.bat runClient` this session, both this bug class:

1. **`AspectRatioModule`/`MenuModule` NPE (26.1.2 crash, not mixin-related)** -- `EUClient.
   MODULE_MANAGER` still null when `Gui.setScreen(TitleScreen)`/`Projection.getMatrix()` fire
   during the client's own boot sequence (main-menu `CubeMap` panorama renders that early now).
   Fixed: null-guards added in `ProjectionMixin.getMatrix$aspectRatio` and `InGameHudMixin.
   euclient$setScreen`.
2. **`ItemInHandRenderer.renderHandsWithItems` MixinApplyError (26.2)** -- real method renamed to
   `submitHandsWithItems` (same signature). Fixed via rename in `ItemInHandRendererMixin`.

Crash #2 triggered a proactive full-repo audit (bash script pulling every `method="..."` string +
INVOKE-target descriptor out of all 75 mixin files, cross-checked against `.port/src26.2` and
`javap` on the real compiled jar) to find other latent instances before the user hit them. Found:

3. **`Gui` -> `Hud` sub-object split**: `extractEffects`/`extractPortalOverlay`/`extractVignette`/
   `extractCameraOverlays`/`extractTextureOverlay`/`extractItemHotbar` all moved off `Gui` onto a

2. **Client actually got in-game this time** (356 ticks / 17.8s played) before a NEW crash:
   `IllegalArgumentException: Maximum capacity of ByteBufferBuilder (1728) exceeded, required 1752`
   in `Renderer3D.buildLines` -> `Renderer3D.draw`, called from the `GameRendererMixin.
   renderWorld$swap` hook, as soon as any debug line (ESP box edges, tracers, etc) actually got
   drawn. Root cause: real `BufferBuilder.endLastVertex()` (confirmed via source) DUPLICATES every
   vertex written in `PrimitiveTopology.LINES` mode into 2 physical buffer slots -- the CPU-side
   "wide line" trick (each 2-point line segment becomes a 4-vertex quad a vertex shader extrudes
   using the paired copies + a lineWidth attribute), not the plain 2-vertices-per-segment the code
   assumed. `Renderer3D.vertexCount(debugLines)` only counted the RAW endpoint count, so
   `ByteBufferBuilder.exactlySized(...)` (a 26.2-only fixed-capacity buffer, no Tesselator
   auto-grow to fall back on) undersized by exactly half. Fixed both LINES-topology allocation
   sites (`Renderer3D.draw`'s debug-lines block, `EspShader.submit`'s debug-lines block) to
   multiply the raw count by 2 before sizing.

`compileJava` and `clean build` re-verified clean after both fixes.

## Session 6: Vulkan backend compat (Options.PreferredGraphicsApi.VULKAN)

User asked about the real in-game "Prefer Vulkan" video setting (`PreferredGraphicsApi` enum,
confirmed in real source: `getBackendsToTry()` tries `VulkanBackend` first when set to VULKAN, falls
back to `GlBackend`). Swept the whole mod for raw LWJGL `GL11`/`GL20`/`GL30` calls -- under a
Vulkan-backend window there's no bound GL context at all, so any raw GL call is a guaranteed crash
(null function pointer), separate from the abstracted `blaze3d` RenderPipeline/GpuBuffer/BufferBuilder
API this whole port already goes through everywhere else. Found 2 real ones (Skia's own GL calls in
`SkiaGlState`/`SkijaBackdropBlur` don't count -- Skia's whole render path is already disabled this
port, see earlier Skia disable-list section):

1. `Renderer2D.project`'s `GL11.glGetIntegerv(GL_VIEWPORT, viewport)` -- replaced with
   `{0, 0, mc.getWindow().getWidth(), mc.getWindow().getHeight()}`, same values GL_VIEWPORT would've
   reported (origin always (0,0)), backend-agnostic since `Window` isn't a GL-specific type.
2. `Renderer3D.draw`'s `GL11.glHint(GL_LINE_SMOOTH_HINT)`/`glEnable(GL_LINE_SMOOTH)`/`glDisable` --
   removed outright, not replaced. Fixed-function GL2 line smoothing is meaningless now that debug
   lines are `POSITION_COLOR_NORMAL_LINE_WIDTH` quads a vertex shader extrudes (see Session 5's
   `buildLines` finding) -- whatever smoothing exists comes from that shader/pipeline, not this
   legacy toggle.

`Prefer OpenGL` (the existing default) was never at risk -- those GL calls always had a real bound
context under GL, this was purely a Vulkan-only crash path. `clean build` re-verified clean after
both fixes.
